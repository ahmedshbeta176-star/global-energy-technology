## Existing database facts used

The current public schema contains these five application tables:

- `profiles(id, full_name, phone, created_at)`
- `stations(id, name, location, capacity_kw, system_type, owner_id, created_at)`
- `station_members(id, station_id, user_id, role_label, is_active, created_at, status, role)`
- `station_member_permissions(id, station_member_id, permission_key, enabled)`
- `station_activity_logs(id, station_id, actor_id, action, details, created_at)`

RLS is enabled on all five tables. Current policies observed: only one SELECT policy on `station_members`, restricting rows to `user_id = auth.uid()`. The other four tables have no policies. The security advisor also flagged the `public.is_station_member(uuid)` SECURITY DEFINER function as executable by anon and authenticated.

## Proposed table-level access rules (to be converted into reviewed SQL)

### profiles
- Authenticated user: read their own profile.
- Authenticated user: update only approved self-service fields (full_name, phone); never id or role/privilege data.
- Founder: administer profiles through a protected server-side path.
- Platform Admin: no blanket access to private profile fields; any support lookup must be narrow, audited, and explicitly granted.

### stations
- Founder: full access.
- Platform Admin: only explicitly delegated operational capabilities.
- Owner: read and update their own station records; deletion should be restricted and audited.
- Active station member: read only stations they are assigned to.
- Technician/Engineer: additional write permissions only when explicitly assigned and necessary.
- Unrelated users and anon: no access.

### station_members
- Founder: full access.
- Station owner: manage memberships for stations they own, excluding any ability to grant platform-level roles.
- Member: read their own membership; no self-activation, role escalation, or permission changes.
- Platform Admin: membership support only when explicitly granted and audited.
- Anon: no access.

### station_member_permissions
- Founder: full access.
- Station owner: grant only an allowlisted set of station-scoped permissions to members of their own station.
- Member: read their own effective permissions only; cannot edit permissions.
- No station-scoped permission can grant platform administration or Founder authority.
- Anon: no access.

### station_activity_logs
- Founder: read all logs.
- Authorized station owner/member: read logs only for stations they are allowed to access, subject to role.
- Inserts should be generated by trusted database/server workflows; users must not forge actor_id or privileged actions.
- Updates/deletes should be denied to ordinary users to preserve audit integrity.
- Anon: no access.

## Critical design requirements

1. Founder identity must be pinned server-side to a trusted immutable auth user UUID / protected allowlist after the actual owner account is verified. Do not guess the UUID or derive authority from editable user metadata.
2. Do not create a public self-service path to Founder or Platform Admin.
3. Avoid broad `SECURITY DEFINER` helpers. Any retained helper must have a fixed safe search_path, carefully reviewed body/ownership, and restricted EXECUTE grants. The current `is_station_member` grants need remediation design.
4. Do not rely on the frontend hiding controls. Enforce access with RLS, grants, and trusted server-side operations.
5. Every privileged action must be attributable and auditable.
6. Define a safe account-recovery procedure for the sole Founder; recovery must not create a routine second Super Admin.
7. No policy may be applied until the owner account, expected product behavior, and negative-access test cases are confirmed.

## Test matrix required before deployment

- anon cannot read or write private profiles, stations, memberships, permissions, or logs.
- User A cannot read or change User B's profile.
- Station owner A cannot access Station B unless separately authorized.
- Active member can read only their assigned station; inactive/revoked member loses access.
- Member cannot add themselves, reactivate themselves, or grant themselves permissions.
- Technician cannot alter station ownership or platform roles.
- Platform Admin cannot grant Founder/Super Admin or change Founder identity.
- Founder can perform intended platform-wide administration.
- Activity logs cannot be forged, edited, or deleted by ordinary clients.
